# スライドデザイン規約

* **適用範囲**: ピッチ資料・Company Deck等、社長室が管掌するデザイン性の高い資料は対象外。
  このskillの対象は、銀行・機関投資家向け提案書や一般的なプレゼン資料など、通常業務で作成する資料
* 配色はパレット9色のみ（CSS の `:root` 参照）。白背景(`#fff`)とキャンバス外の背景(`#e7eef4`)は
  スライド構造上の既定値であり、この9色の対象外(追加のアクセントカラーとして使わないこと)。
  積み上げ棒グラフの系列色(`--chart-1`〜`--chart-4`)も別建て(mainの明度4段。隣接セグメントの
  識別性を確保するためで、新しい色相は足していない)。
  グラデーション・影・その他の色は禁止。9色すべてこのデザイントークンのパレットと完全一致させること
  (hexコードを独自に調整しない)
* フォントは Noto Sans JP のみ(CSS内のヒラギノ等は未インストール環境向けのフォールバックで、
  意図的な代替フォントではない)。読ませる文字は最低 14px（10.5pt）、本文標準 17px。
  文字を小さくして収めるのではなく、文章を削って収める
* 原則白背景。カラム・囲みは「塗：`#eef1f4`／線なし」。黒線・青線での囲み禁止。
  角丸は辺の10%以下かトラック型に振り切る
* 矢印は三角のみ（■+▼の自作矢印禁止）。アイコンはフラットな青系のみ
* AIっぽさ排除: 絵文字ビュレット禁止／1スライド1メッセージ／カード4枚以上並べない／
  強調は1スライド2〜3箇所まで／根拠のない数字を新造しない
* 表は3〜4列を目安にする。列を増やすほど1セルに入れられる強調・注釈が減り、
  「強調は1スライド2〜3箇所」を守れなくなったり、注釈(`small-note`)の折り返しで
  縦にはみ出したりしやすい(実測で判明した失敗パターン)。5列以上必要なら、
  列を削るか複数スライドに分けることを先に検討する
* 表の`<th>`は**全列に`width:`を明示指定する**(最初の列だけ指定して残りを空けると、
  ブラウザが各列のテキスト量で自動配分し列幅が不揃いになる。実測で判明した失敗パターン)。
  役割が同じ列(比較の選択肢・RACIの担当者・ジャーニーの段階等)は完全に均等%で割り、
  ラベル列など性質が違う列だけ別の%にする(例: ラベル列28% + 均等列24%×3 = 100%)
* 空白を締める（最重要）: 下1/3が空いたスライドを作らない。
  「タイトル＋リード → 本文（縦いっぱい）→ キーメッセージ帯」で構成し、
  埋まらないなら ①文字を1段階大きく → ②図版を大きく → ③枚数を減らす。
  例外は表紙・扉のみ
* フッター（出典）は絶対配置禁止。`.slide-footer` のフロー配置のまま使う

## 納品前チェック(必須・2段階)

### Step A: 数値チェック(over/clipped/強調過多)

作成したHTMLをブラウザで開き、画面上で右クリック→「検証」(または F12)→Consoleタブを開いて
以下を貼り付けて実行し、全スライドで `over: 0`・`clipped: 0`・`overEmphasis: 0` を確認する。
`overEmphasis` が1のスライドは強調(`.em` `.em-hl` `.attn` `.attn-hl`)が4箇所以上ある(規約違反)ので、
重要度の低い強調を外して3箇所以下にする。

(GUIブラウザを操作できないCLI環境で作業している場合は、headless Chrome を
`--remote-debugging-port` 付きで起動し、Chrome DevTools Protocol(WebSocket)経由で
同じJSを `Runtime.evaluate` すれば同等のチェックができる。ロジックは同一、実行手段が違うだけ)

```js
[...document.querySelectorAll('.slide')].map((s, i) => {
  const emphasisCount = s.querySelectorAll('.em, .em-hl, .attn, .attn-hl').length;
  return {
    page: i + 1,
    over: s.scrollHeight - s.clientHeight,
    clipped: [...s.querySelectorAll('.box, .slide-body, .takeaway, .funnel-stage, .radar, .tree, .tree-leaf, .kpi-tile')]
      .filter(b => b.scrollHeight - b.clientHeight > 1).length,
    /* 注: .wf-col(ウォーターフォールの棒グラフの列)はチェック対象外。棒が浮動配置される設計上、
       列自身の箱からラベル・数値がはみ出すのが正常なため、この判定方法では誤検知になる。
       ウォーターフォールは目視、または .slide 全体の over のみで確認する */
    /* 注: .fd-branch(基盤展開図の分岐ボックス)も同じ理由でチェック対象外(公式リストに含めない)。
       接続線のラベル(.fd-connector-label)がボックス外(bottom:負の値)に意図的にはみ出す設計のため、
       .fd-branch を対象に含めると誤検知する(実測で確認済み)。基盤展開図も目視で確認する */
    emphasisCount,
    overEmphasis: emphasisCount > 3 ? 1 : 0
  };
})
```

### Step B: 目視チェック(必須。Step Aだけで済ませない)

Step Aの数値チェックは「はみ出し」「強調過多」しか検知できない。**技術的にはoverflowしていなくても
見た目が崩れているケース` (タイトルが1文字だけ2行目に落ちる不格好な折り返し、`.tree` の接続線が
分岐の外側まで宙に浮いて伸びる、等) はこのJSだけでは発見できない**。必ずスクリーンショットを撮って
全スライドを目視確認してから納品する(ブラウザで開けない環境では、headless Chrome の
`--screenshot` オプションで画像化してから確認する)。

## PDF変換(フォントが崩れない方法。macOS/Linux。Windowsはブラウザの「印刷→PDF保存」機能で代用可)

**単純な `--print-to-pdf` コマンドは使わないこと。** Webフォント(Noto Sans JP)のダウンロードが完了する前に
印字してしまい、代替フォント(Times やヒラギノ)のまま固定されることがある(実測で確認済み。読み込み直後は
`document.fonts.status` が `loaded` を返しても実際には未適用で、`Times` 等になっている場合がある)。
**`document.fonts.ready` を待ってから印字する** `_tools/slide_style/print-pdf.mjs`(このskillが自動でコピーする。
追加パッケージのインストール不要、Node組込みの `fetch`/`WebSocket` のみで動く)を使う。

```bash
node _tools/slide_style/print-pdf.mjs 入力.html 出力.pdf
```

(Noto Sans JP をローカルにOTFインストール済みの場合はネットワーク不要で即座に読み込まれるため、
このコマンドはインストール有無に関わらず安全に使える。未インストール環境ではCDN取得を待つだけ)

`print-pdf.mjs` は書き出し後に出力PDFへ埋め込まれたフォント名を抽出し、標準出力に報告する
(事前の `document.fonts.ready` 待ちが機能したかの事後検証)。`NotoSansJP` 以外(`Hiragino*`等)が
報告されたら、フォント待ちに失敗している(代替フォントで固定された)ので再実行する。
