# 提案構成フレームワーク

見た目(デザイン規約.md)を整える前に、まず中身の論理構成(ストーリーライン)を設計する。配色・レイアウトが良くても、話の運びが悪ければ資料としては失敗する。

## 実証済みの型(機関投資家向け提案書パターン)

金融機関向け提案書で一般的に用いられる構成順。新規に提案書を作るときは、まずこの型に当てはめて章立てを作り、対象読者に不要な章は削ってよい(全章を機械的に埋めない)。

1. 表紙
2. 御社が直面されている課題(2〜3個。テーブルで具体的な影響を明示)
3. ご提案の概要(「既存構成への追加」という形で導入ハードルを下げる)
4. サービス内容(設計思想 → 運用体制 → 対応範囲の順)
5. 収益・効果シミュレーション(具体的な数字。試算根拠を必ず明記)
6. 仕組みの説明(動作原理・データの流れ)
7. セキュリティ・リスク対策
8. 料金体系(初期費用の低さ・導入障壁の低さを明示)
9. 他社比較(表形式。自社の優位点を定量・定性で並記)
10. 導入までの流れ(ステップ形式。各ステップの相手側の負荷を明示)
11. 運営体制(信頼性の裏付け)
12. 次のステップ(Call To Action。問い合わせ先を明記)
13. Appendix(契約・コンプライアンス詳細、補足比較)

## 章ごとに使う外部フレームワーク

| 章 | フレームワーク | 適用ルール |
|---|---|---|
| 冒頭(表紙〜課題) | SCQA | Situation(相手も同意する現状)→Complication(規制変化・リスク等)→Question(自然に生まれる問い)→Answer(次章で提案概要へ)の順で1〜2枚に収める |
| 課題認識 | 3C分析 | 自社(Company=提案先の既存体制)／顧客(Customer=エンドユーザーや規制当局の要求)／競合(Competitor=他プロバイダー)の3視点で課題を整理してから提案概要に接続する |
| 価値訴求(サービス内容) | Value Proposition Canvas | 相手のPains(規制対応負荷・運用リスク等)とGains(収益機会・信頼性)を先に書き出し、各項目に自社機能を1対1で紐付ける |
| 全章共通 | Pyramid Principle | 各章の最初のスライドタイトルに結論を1文で書き、以降のスライドはその結論を裏付ける理由・データの並びにする(理由はMECEに、重複・漏れをなくす) |
| 全スライド共通 | Answer First / 1スライド1メッセージ | スライドタイトルは名詞句でなく「結論を言い切る一文」にする。1スライドに主張は1つだけ(デザイン規約.md の「1スライド1メッセージ」と同じ思想) |
| 他社比較 | 2軸ポジショニングマップ(BCGマトリクス等でおなじみの型) | 相手にとって意味のある2つの評価軸(例: 横軸=導入のしやすさ、縦軸=管理負荷の低さ)を選び、自社と競合をプロットする。自社は必ず有利な象限(右上が基本)に位置するよう軸の向きを選ぶ。表による比較と両方使ってもよいが、重複しすぎる場合はどちらか一方に絞る |
| 収益・効果シミュレーション | ウォーターフォール(ブリッジ)チャート | 「合計だけ」でなく「何が増減に効いたか」を見せたい時に使う(例: 前年実績→新規獲得→解約→単価改定→当年実績)。数字を新造しない(デザイン規約.mdの原則どおり、根拠のある増減要因のみ) |
| 市場規模・商談パイプライン | ファネル(TAM-SAM-SOM等) | 「全体からどれだけ絞り込まれるか」を見せたい時に使う(例: TAM→SAM→SOM、リード→商談→受注)。3〜4段が目安(5段以上は帯が細くなりすぎる) |
| 他社比較(多軸) | レーダー(スパイダー)チャート | 評価軸が3つ以上あり、かつ「総合力」を面積で見せたい時に使う(2軸なら2軸ポジショニングマップの方が読みやすい)。軸は必ず5つ固定(`reference/template.html` スライド9の座標がそのまま使えるのは5軸の時のみ)。比較対象は2系列まで(3系列以上は塗りが重なって読めなくなる) |
| 論点の構造化・意思決定の根拠整理 | イシューツリー(MECE分解図) | 「なぜそう言えるか」を階層的に分解して見せたい時に使う(例: 新規参入すべきか→市場性/勝ち筋/実行可能性)。下位論点は2〜4個(重複・漏れがないか=MECEを自問する)、各下位論点の裏付け事実は1〜3個が目安 |
| 実績サマリー | KPIスタットタイル | 「主要指標を数字で一覧させたい」時に使う(例: 導入行数・収益・AUM・SLA実績)。3〜4枚が目安(5枚以上は1枚ずつが小さくなる) |
| 施策の優先順位付け | 優先度(Impact-Effort)マトリクス | 2軸ポジショニングマップに象限ラベル(Quick Win/大型プロジェクト/すぐ着手可/後回し)を重ねた版。複数の施策・打ち手のどれから着手すべきかを一目で示したい時に使う |
| 課題認識(内部要因を細かく) | SWOT分析 | 3Cより粒度細かく自社の内部要因(強み・弱み)と外部要因(機会・脅威)を整理したい時に使う。3Cと両方使うと重複するので、どちらか一方に絞る |
| 冒頭(なぜ今か) | PEST(PESTEL)分析 | 「なぜ今提案するのか」をマクロ環境(政治・経済・社会・技術)の追い風として裏付けたい時に使う。SCQAのComplication(C)を補強する位置づけ |
| 課題認識(業界構造) | 5フォース分析(Porter) | 自社が置かれた競争環境を「業界内競争・新規参入・代替品・供給者・買い手」の5つの力で俯瞰したい時に使う。他社比較(2軸マップ)の前段の状況整理として使う |
| 提案概要(ターゲット定義) | STP分析 | 「誰に・何を訴求するか」を市場細分化(S)→ターゲット選定(T)→立ち位置の言語化(P)の順で定義したい時に使う |
| サービス内容(全体像) | ビジネスモデルキャンバス | サービス内容の詳細(設計思想→運用体制→対応範囲)に入る前に、事業構造を9ブロックで1枚に俯瞰したい時に使う |
| 導入までの流れ(体験ベース) | カスタマージャーニーマップ | ステップ形式の「導入までの流れ」だけでは伝わらない、相手側の感情・課題の変化まで見せたい時に使う |
| ご提案の概要(位置づけ) | アンゾフの成長マトリクス | 「既存構成への追加」という提案の位置づけを、市場×製品の2軸でリスクの低さとして裏付けたい時に使う |
| 導入までの流れ(複数施策が並行) | ロードマップ(ガントチャート) | ステップ形式では表現しにくい、複数の施策・工程が並行して進む導入計画を時系列で示したい時に使う |
| 運営体制 | RACIチャート | 導入後の役割分担(誰が実行し・誰が説明責任を負い・誰に相談し・誰に報告するか)を工程ごとに明確化したい時に使う |
| 事業計画(内訳×推移) | 積み上げ棒グラフ | 複数事業・複数カテゴリの内訳が、年を追ってどう積み上がるかを一目で見せたい時に使う(例: 事業別売上高の5年推移) |
| 事業構造(資産の活用) | 基盤展開図 | 1つのコア事業が積み上げた資産(顧客基盤・データ・知見等)を使って複数の事業が派生する構造を示したい時に使う |

## 適用例(具体的な型)

フレームワーク名を意識するだけでは、実際の中身が一般的な説明になりがちなので、以下の型に literally 当てはめて書く。

**冒頭(SCQA)**: 「現状説明→提案」といきなり繋げるのではなく、以下の4パーツが揃っているか確認する。実装は `.box` 3つ(S/C/Q)+ `.takeaway`(A、次章への接続文)の組み合わせで良い(専用CSSクラスは無い)。

| パーツ | 書く内容の例 | 満たすべき条件 |
|---|---|---|
| S(Situation) | 「現在、暗号資産の運用を検討する金融機関が増えている」 | 相手が読んで反論しない、両者合意済みの事実のみ |
| C(Complication) | 「一方で、海外プロバイダー中心では委託先管理の負荷が高い」 | Sとのギャップで初めて緊張感を作る(Sの時点で書かない) |
| Q(Question) | 「では、管理しやすく信頼できる委託先をどう確保するか」 | S→Cから読者の頭に自然に浮かぶ問いにする(唐突な問いにしない) |
| A(Answer) | 「それが本サービスです」(次章「ご提案の概要」への接続文のみ) | この時点で結論を1文で言うだけに留め、詳細は次章以降に譲る |

**課題認識(3C)**: 「困りごとを3つ並べる」のではなく、以下の3行になっているか確認する。

| 視点 | 書く内容の例 |
|---|---|
| 自社(Company) | 提案先の既存の資産管理体制・運用方針(例: 秘密鍵をどこで管理しているか) |
| 顧客(Customer) | 提案先のエンドユーザーや規制当局が求めていること(例: 説明責任・開示要求) |
| 競合(Competitor) | 他プロバイダーを使う場合の制約(例: 英語対応・海外タイムゾーン・契約確認の工数) |

**価値訴求(Value Proposition Canvas)**: 「機能の説明」を並べるのではなく、以下のPain/Gain → 自社機能の対応表になっているか確認する。

| 相手のPain/Gain | 自社機能 |
|---|---|
| Pain: 規制対応・委託先管理の負荷が高い | → 日本語窓口・国内オフィスでの一次対応 |
| Pain: 秘密鍵を預けることの管理リスク | → Non-Custodial設計(鍵を預からない) |
| Gain: 追加コストなく新しい収益機会を得たい | → 初期費用ゼロの成功報酬型 |

**他社比較(2軸ポジショニングマップ)**: `.matrix2x2` クラス(slide_style.css・template.htmlのスライド6参照)を使う。軸の選び方が肝で、「自社が強い軸」ではなく「相手が意思決定で重視する軸」を選ぶこと(例: 金融機関向けなら「委託先管理のしやすさ」「非保管(Non-Custodial)度合い」等)。プロット位置は `left`/`top` をパーセントで指定し、**`top` は数値が小さいほど軸の上(＝その軸で評価が高い)側になる**(`top:15%` は上寄り、`top:78%` は下寄り)。自社は右上(`left` 大きめ・`top` 小さめ)に来るよう軸の向きを選ぶ。競合の実名を出す場合、公開情報に基づく一般的な比較である旨をスライド下部に注記する。

**収益・効果シミュレーション(ウォーターフォール/ブリッジチャート)**: `.waterfall` クラス(slide_style.css・template.htmlのスライド7参照)を使う。手順:
1. 起点・増減・終点の値を並べる(例: 前年100 → 新規+30 → 解約−15 → 単価改定+10 → 当年125)
2. `max_scale` を、最も高くなる累計値より少し大きい値に決める(上記例なら140)
3. 各棒の `height%` = `|値| / max_scale * 100`
4. 起点・終点の棒(`total`)は `bottom:0%`
5. 増加の棒(`pos`)は `bottom: 変化前の累計/max_scale*100%`、減少の棒(`neg`)は `bottom: 変化後の累計/max_scale*100%`(＝低い方に揃える)
6. 隣り合う棒の上端・下端が階段状につながっているか(前の棒の上端 ＝ 次の棒の下端になっているか)を目視で必ず確認する

**市場規模・商談パイプライン(ファネル)**: `.funnel` クラス(slide_style.css・template.htmlのスライド8参照)を使う。**`width%` と `fs-conv` は分母が異なるので混同しない**:
- `.fs-bar` の `width%` = その段の値 ÷ **一番上の段**の値 × 100(基準は常に最上段)
- `.fs-conv` = その段の値 ÷ **1つ上の段**の値 × 100(基準は毎回1つ上の段。最終段に近づくほど width% と値が乖離していく)

**他社比較(レーダー/スパイダーチャート)**: `.radar` クラス(slide_style.css・template.htmlのスライド9参照)を使う。**背景の同心五角形グリッド・軸線・軸ラベルの座標は固定なので変更しない**(5軸専用に計算済み)。変更してよいのは `<polygon class="series-a">`(自社等) と `<polygon class="series-b">`(競合等)の `points` 属性、および軸ラベルの文言、凡例の文言のみ。データ点の計算式(テンプレートのコメントに全文あり):
1. 5軸それぞれの方向単位ベクトル(テンプレートのコメントに記載済み。軸の順番は「真上→時計回りに右上・右下・左下・左上」で固定)
2. 各軸のデータ点のSVG座標 = 中心(220,200) + 方向ベクトル × (値÷満点) × 最大半径150
3. 5軸分の座標を計算したら、`points="x1,y1 x2,y2 x3,y3 x4,y4 x5,y5"` の順(軸の順序どおり)で並べる

**論点の構造化(イシューツリー)**: `.tree` クラス(slide_style.css・template.htmlのスライド10参照)を使う。構造は `.tree-root`(ルートの論点・1個)→ `.tree-level` の中に `.tree-branch` を2〜4個(下位論点)→ 各 `.tree-branch` の中に `.tree-node`(下位論点の文言・1個)と `.tree-leaves` の中に `.tree-leaf` を1〜3個(裏付け事実)。座標計算は不要(すべて自動レイアウト)。下位論点を書く時に「重複していないか(MECE)」「足りない論点がないか」を自問すること。

**実績サマリー(KPIスタットタイル)**: `.kpi-row` の中に `.kpi-tile` を3〜4個並べる(slide_style.css・template.htmlのスライド11参照)。各タイルは `.kpi-value`(大きな数字。単位は `.kpi-unit` で一回り小さく)・`.kpi-label`(指標名)・`.kpi-delta`(前年比等。プラス方向は `up` クラス、マイナス方向は `down` クラス)の3点構成。座標計算は不要。

**施策の優先順位付け(優先度マトリクス)**: `.matrix2x2` の中に `.quad-label` を4つ追加するだけ(slide_style.css・template.htmlのスライド12参照)。象限ラベルの位置は固定(左上25%/15%・右上75%/15%・左下25%/85%・右下75%/85%、いずれも `transform:translate(-50%,-50%)` 付き)。`.matrix-point` の位置だけ、2軸ポジショニングマップと同じ考え方(topが小さいほど上)で施策ごとに変更する。

**課題認識(SWOT分析)**: `.quad-grid` の中に `.quad-cell` を4つ(slide_style.css・template.htmlのスライド13参照)。座標計算は不要(CSS Gridで自動配置)。配置は固定で左上=強み・右上=弱み・左下=機会・右下=脅威(内部要因が上段・外部要因が下段)。ポジティブな象限(強み・機会)は `q-pos`、ネガティブな象限(弱み・脅威)は `q-neg` を付けて色分けする。3C分析と両方使うと重複するので、自社の内部要因をより細かく見せたい時だけSWOTを選ぶ。

**冒頭(PEST分析)**: `.quad-grid` を中立版(`q-pos`/`q-neg` を付けない)で使う(template.htmlのスライド14参照)。4象限は政治・経済・社会・技術で固定。各セルの見出しには `.num` バッジ(数字でなくP/E/S/Tの頭文字)を置き、視覚的なアンカーにする。目的はSCQAのComplication(C)を補強する外部環境の裏付けであり、自社評価ではないので色分けしない。

**課題認識(5フォース分析)**: `.forces` の中に `.forces-center`(中央=業界内競争)と `.forces-item`(周囲4方向)を配置する(slide_style.css・template.htmlのスライド15参照)。座標計算は不要(CSS Gridの `grid-template-areas` で固定配置、位置クラスは `top`/`bottom`/`left`/`right` の4つのみ)。接続線・矢印は描かない(過去にイシューツリーの接続線で座標バグが発生した経緯があり、5フォースはグリッド隣接だけで力関係を表現する設計にしている)。

**提案概要(STP分析)**: `.stp-flow` の中に `.box`(既存クラスをそのまま流用)を3つ、`.tri-arrow` で繋ぐ(slide_style.css・template.htmlのスライド16参照)。S→T→Pの順で「市場を切る→狙う層を絞る→立ち位置を一言で言い切る」の3段が揃っているか確認する。Positioningは1文で言い切ること(3行以上の説明にしない)。

**サービス内容(ビジネスモデルキャンバス)**: `.bmc-grid` に9つの `.bmc-cell` を配置する(slide_style.css・template.htmlのスライド17参照)。各セルの `class` は固定(`kp`=主要パートナー・`ka`=主要活動・`vp`=提供価値・`cr`=顧客関係・`cs`=顧客セグメント・`kr`=主要リソース・`ch`=チャネル・`cost`=コスト構造・`rev`=収益の流れ)で、位置はCSS側で決まっているため変更不要。**文言は名詞句(体言止め)で書く**(9ブロックに文章を詰めると14px下限を割るか溢れるため、「文章を削って収める」の原則を徹底する)。

**導入までの流れ(カスタマージャーニーマップ)**: 既存の `<table>` をそのまま使う(新規CSSクラス不要。template.htmlのスライド18参照)。列=導入後の体験の段階(4段が目安、5列以上は複数スライドに分けることを検討)、行=行動・感情・課題の3行が基本。感情行は既存の `.em`(ポジティブ)・`.attn`(要注意)をそのまま流用し、色を増やさない。

**ご提案の概要(アンゾフの成長マトリクス)**: `.quad-grid` を再利用する(SWOTと同じCSS。template.htmlのスライド19参照)。配置は固定で左上=市場浸透(既存市場×既存製品)・右上=新製品開発・左下=新市場開拓・右下=多角化(縦軸=製品の新旧、横軸=市場の新旧)。「既存構成への追加」提案は必ず市場浸透(左上、最もリスクが低い象限)に位置づけ、`q-pos` で色分けする。

**導入までの流れ(ロードマップ/ガントチャート)**: `.gantt` の中に `.gantt-row` を施策の数だけ並べる(slide_style.css・template.htmlのスライド20参照)。各行の `.g-bar` の `left%`/`width%` は、期間全体を100%とした按分値をインラインで指定する(例: 全体6か月中、1〜2か月目に実施する施策なら `left:0%; width:33%;`)。マイルストーン(本番稼働等の単発イベント)は `milestone` クラスでアクセント色にする。ステップ形式の `.flow` は「順番」を見せる時、ガントチャートは「並行して進む複数施策の時間軸」を見せたい時に使い分ける。

**運営体制(RACIチャート)**: 既存の `<table>` をそのまま使い、セルに `.raci-badge`(クラスは`r`/`a`/`c`/`i`の4色だが、中身のテキストは英字略号でなく**日本語ラベル「実行/責任/協力/報告」を直書き**する。凡例なしでも意味が伝わるようにするため。新規テーブルCSS不要。template.htmlのスライド21参照)を置くだけ。1つの工程(行)に `a`(責任=説明責任者)は必ず1つだけにする(2つ以上あると責任の所在が曖昧になり、RACIの意味が崩れる)。

**事業計画(積み上げ棒グラフ)**: `.stack-bar` の中に `.sb-legend`(カテゴリ凡例)と `.stack-bar-chart`(年ごとの `.sb-col`)を置く(slide_style.css・template.htmlのスライド22参照)。`.sb-bar` は `flex-direction:column-reverse` なので、**DOM順=積む順で最初に書いた `.sb-seg` が最下段**になる(主力事業を最初に書く)。カテゴリは `c1`〜`c4` の4色まで(5カテゴリ以上必要ならカテゴリを統合するか複数スライドに分ける)。各 `.sb-seg` の `height:%` は、その年の合計を100%とした構成比を指定する。

**事業構造(基盤展開図)**: `.foundation-diagram` の中に、上段の `.fd-branches`(`.fd-branch` を3〜4個)と下段の `.fd-base` を置く(slide_style.css・template.htmlのスライド23参照)。接続線は `.fd-branch::after` が自動で引く直線のみで、**曲線矢印は描かない**(過去にイシューツリーの接続線でz-orderバグが発生した経緯があり、基盤展開図も直線方式に統一して同じ轍を踏まない設計にしている)。各分岐が土台から得ている資産(顧客基盤・データ・知見等)は `.fd-connector-label` で線の途中に短く添える。5分岐以上は1本あたりの横幅が狭くなり文字が収まらないため、4分岐までを目安にする。

## 書き始める前のセルフチェック(MEDDIC由来)

- 決裁者は誰か → その決裁者が重視する指標(コスト・リスク・スピード等)に応える章があるか
- 決裁プロセス(稟議等)は何か → 導入までの流れの章がその負荷に触れているか
- 何をもって「良い提案」と判断されるか → 比較章がその基準で書かれているか

## 対比として採用しない型

- PAS(Problem-Agitate-Solution)のように不安を煽る強い型は、金融機関相手の提案では基本的に不採用(SCQAで足りる場合はSCQA優先)
- 「箇条書き禁止・全文章体」のドキュメント文化(Amazon方式)は、デザイン規約.md の箇条書き中心スタイルと相性が悪いため採用しない
